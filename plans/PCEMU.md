## 0. Binding decisions

1. **The machine, not an API.** `PCEmulator.app` emulates hardware at the
   register level, and everything above the hardware (BIOS, DOS, shell,
   utilities, drivers) runs on the emulated machine. Any DOS or boot disk the
   user supplies boots and runs exactly as on the hardware it models.

2. **Every line is Rust, the guest included.** No third-party BIOS, DOS or
   utility binary is shipped or fetched. The BIOS, TAIRiX DOS, COMMAND.COM and
   the utilities are Rust running as *host calls*: an encoding that is invalid
   on every modelled CPU (`FE 38 lo hi`), honoured only when executed from the
   emulator's own ROM pages, stops the CPU and hands the machine to Rust with
   the call number. Executed anywhere else it does what the modelled CPU does.
   ROM stubs, boot sectors and test programs are emitted by the crate's own
   x86-16 encoder, never assembled from text.

3. **Guest state lives in guest memory.** The BIOS keeps its state in the BIOS
   data area. TAIRiX DOS keeps its PSPs, MCB chain, SFT, CDS, DPBs, buffers,
   device chain, swappable data area and List of Lists in guest memory, where
   programs that walk or patch DOS internals find them. COMMAND.COM keeps its
   state in its own memory block. Rust holds only derived caches, so a snapshot
   is guest memory plus device registers, and nested guest execution (a device
   driver's strategy routine, INT 13h through the guest vector, INT 23h, 24h
   and 28h) cannot corrupt Rust state, only the guest's — the same contract real
   DOS keeps. Nesting is bounded and fails closed beyond the bound.

4. **The guest is hostile.** Guest code, guest memory and every disk image are
   untrusted input. They are interpreted only inside a capability-empty
   sandbox (PC14). Every host-call handler is total over guest state: a
   malformed request is the error the real service would return, never a
   panic, an unbounded loop or an unbounded allocation. Cluster chains,
   directory walks, MCB walks and device chains carry hop bounds.

5. **Three processes.**

   | Process | Does | Holds |
   |---|---|---|
   | Front-end (`Run`) | windows, the library, settings, audio stream, disk images, the user's grants; relays compile requests; performs the BR26 flip | the bundle's grant |
   | Machine worker | the CPU, board, devices, BIOS, DOS; the interpreter and installed translations | nothing: a canonical sandbox with one spawn share |
   | Compiler | translates guest blocks to host code into a region it fills | nothing: a canonical sandbox |

   The front-end parses nothing a guest controls beyond the session framing:
   it validates every frame field (slot indices, sector ranges, lengths) and
   answers a malformed frame by ending the worker. The compiler never runs what
   it writes, the worker never holds a writable and executable mapping, and the
   front-end never reads compiled code.

6. **The interpreter is permanent.** It defines the machine's behaviour, runs
   when translation is refused or unavailable (wasm32, a missing capability, a
   failed compiler), and is the oracle the translator is fuzzed against. The
   translator is an addition: an installed block is an exact replacement for
   the interpreter over its guest bytes, invalidated by any write to them.

7. **Time is emulated, not sampled.** Emulated time is a `u64` count of
   nanoseconds. Every clock domain (CPU, PIT, CRTC, FDC, UART, OPL, DSP)
   converts from it by an exact rational over `u128`, so no domain drifts.
   Devices catch up lazily when touched and schedule only the events that raise
   interrupts or DMA. The worker paces emulated time to the host's monotonic
   clock and waits on its pipe with a deadline between slices, so an idle or
   halted guest costs no host CPU. *Turbo* raises the CPU's cycles per unit of
   emulated time and never speeds the devices, so a guest clock stays true.

8. **Timing fidelity.** Instructions take the manufacturers' published cycle
   counts per model, corrected to what hardware bus traces measure wherever a
   trace exists, with effective-address cost on the 8086 family,
   data-dependent multiply and divide taken from the microcode's own loop
   paths, and memory wait states. The prefetch queue is modelled for its
   observable effects: a write into bytes already queued does not change what
   executes, and an instruction waits for bytes the queue has not yet
   fetched, which refills only while the execution unit leaves the bus idle.
   Bus-cycle-exact (T-state) interleaving is not modelled.

9. **Memory.** Conventional memory is configurable in 64 KiB steps to 640 KiB.
   Above it, an LIM EMS 4.0 board of up to 8 MiB, the 8-bit era's specification
   ceiling (EMS 3.2), maps 16 KiB pages into a 64 KiB frame by page-table
   update, never by copy.

10. **Storage.** A machine's disks are user documents (read-write picks) or
    blobs in the application's own store. Blobs are bounded at 64 MiB each
    (`plans/APPDATA.md` §3.8), which holds every period disk. The default
    30 MB disk is *generated* (PC13), not shipped: the load gate refuses a
    bundle file over 16 MiB, and a generated image is sparse, so it costs only
    what the guest writes.

11. **Presentation.** The worker renders each frame at the card's native
    resolution into the spawn share; the front-end scales it with the correct
    4:3 aspect through `lib/raster`'s frame scaler (`SharpScaler`): each source
    pixel a block of whole output pixels, only the output pixel at a block's
    edge blended, its taps kept per pair of sizes, and only the rows a changed
    source row reaches redrawn. It measures under 1.4 ns a pixel portable, a
    copy almost everywhere, so it has no vector candidates; the exact asset
    resampler is not used per frame (`plans/FIX-DESKTOP-SPEEDUP.md` F.3). The
    CRT model (scan lines, phosphor persistence, glow) is the terminal's
    pipeline hoisted into `lib/crt` rather than written twice.

12. **Input.** A focused machine window takes the raw keyboard (every physical
    key's make and break, modifiers and locks included; the session keeps
    Ctrl+Alt+Delete, which the window offers as a command). The guest's own
    typematic generates repeats, not the host's. The keyboard is the enhanced
    101-key keyboard in XT mode: an XT BIOS reads an `E0` prefix as the release
    of a key it lacks, so the grey keys reach it as the keypad's, kept true to
    their labels by the fake shifts IBM's enhanced keyboard sends, Num Lock
    counted by the keyboard itself; Pause and Print Screen send what an XT BIOS
    reads as Ctrl+Num Lock and Shift+`*`. The mouse is seamless while TAIRiX
    DOS's own INT 33h driver holds both the INT 33h vector and its port's IRQ
    vector: the front-end sends where the host pointer is over the screen, the
    serial mouse still sends a packet for each change, and the driver takes its
    position from the host pointer rather than from the packet, so any other
    driver still moves. The host cursor is hidden over the screen. Whenever
    either vector is someone else's, the program is reading the mouse itself
    and gets pointer lock, released by a lone tap of the Meta key, which no
    modelled keyboard has.

13. **Fonts.** The MDA, CGA, EGA and VGA character generators are first-party
    code page 437 bitmaps at 8×8, 8×14 and 8×16, authored as reviewable text in
    the crate and compiled into the ROMs. No IBM font is copied.

## 1. The machine

### 1.1 CPU (PC1)

- **Models.** `CpuModel::{I8088, I8086, V20, V30, I80188, I80186}`. Bus width,
  queue length (4 bytes on 8-bit buses, 6 on 16-bit), instruction set, timing
  table and undocumented behaviour are per model.
- **One decoder** produces a compact `Instruction` (opcode class, operands,
  ModRM effective address and default segment, prefixes, length). The
  interpreter, the translator's front end and the debugger's disassembler all
  use it, so there is one definition of what the bytes mean.
- **Instruction sets.**
  - 8086/8088: the full documented set, and the undocumented forms software
    relies on: `POP CS` (`0F`), `60`–`6F` as conditional jumps, `C0`/`C1`/`C8`/
    `C9` as returns, `SALC`, `F1` as `LOCK`, `D0`–`D3 /6` (`SETMO`/`SETMOC`),
    segment-register fields that decode two bits, `MOV CS`, AAM/AAD with any
    base, unmasked shift counts, `PUSH SP` pushing the decremented value, the
    IDIV range that refuses −128, REP negating MUL and IDIV results, the
    resumption of an interrupted string instruction with only its last prefix,
    and interrupt inhibition after any segment-register load.
  - 80186/80188 add `PUSHA`, `POPA`, `BOUND`, `PUSH imm`, `IMUL imm`, `INS`,
    `OUTS`, shifts by immediate, `ENTER`, `LEAVE`, the invalid-opcode trap
    (INT 6) and the ESC trap (INT 7) when the relocation register's ET bit is
    set; shift counts are masked to five bits.
  - V20/V30 add the 80186 set (without the 80186's peripherals) and the NEC
    extensions: the `0F`-prefixed bit operations, `ADD4S`/`SUB4S`/`CMP4S`,
    `ROL4`/`ROR4`, `INS`/`EXT`, `REPC`/`REPNC`, and AAM/AAD fixed to base ten.
    The 8080 emulation mode (`BRKEM`) is part of PC1.
- **Flags.** Bits 12–15 read as one on every modelled CPU; arithmetic flags are
  computed exactly, including the documented-undefined ones whose real values
  are known.

### 1.2 Board (PC2)

- **Scheduling.** Devices are lazy: the board catches them up to the CPU's
  cycle count whenever the CPU touches one, and reports the next instant one
  must act on its own — an unmasked IRQ edge, a keystroke's byte, an 80186
  timer or timer-paced DMA. `Machine::run_until` runs the CPU in slices that
  end there; a device write ends a slice early (`Stop::Rescheduled`) so the
  new schedule is read, and a halted CPU skips to the next event. Refresh is
  charged per instruction against a precomputed next-refresh cycle, so it
  slows the CPU as it runs rather than when a device is next touched.
- **Memory map.** 256 pages of 4 KiB, each an offset into one store or the
  open bus (`FFh`); ROM pages ignore writes and only the emulator's own ROM
  honours the host call. Memory accesses carry the cycle count, and the
  prefetch queue's captures use a side-effect-free `peek`. Wait states are a
  1 KiB table, with a per-access path for a kilobyte the 80186's peripheral
  selects split. Device-mapped pages arrive with video (PC3), EMS mapping
  with PC8.
- **Ports.** Ten-bit decode through a 1024-entry table; the planar decodes
  A9–A5 below `100h`. Every I/O cycle carries one wait state; word I/O
  reaches a 16-bit device as one access and an 8-bit one as two.
- **Chips.** The 8259A (every ICW and OCW, rotation, special mask, special
  fully nested, MCS-80 vectors); the 8253 (six modes, BCD, latch, no
  read-back; modes 2 and 3 reload at the period or half-period end; held to
  a clock-by-clock data-sheet oracle); the 8237 (auto-init, the 64 KiB page
  wrap, and the PC/XT's write-only 4 × 4-bit page register file, channels 0
  and 1 sharing `83h`); the 8255 (reset to all inputs; the 5150's SW1-on-port-A
  and SW2 wiring, the 5160's SW1 nibbles); the 83-key keyboard (scan code set
  1, its own typematic, the 20 ms clock-low reset and self-test, a 16-byte
  buffer with overrun); and DRAM refresh, timer 1's rises requesting DMA
  channel 0, five cycles each.
- **NMI.** The mask at `A0h` and its one source, the coprocessor: §1.8.
- **80186/80188.** The peripheral control block at its relocation register
  (I/O `FF00h` from reset, or memory space), answering word I/O inside the
  CPU and byte accesses into their half: the interrupt controller in master
  mode with INT0 cascading the 8259A (in slave mode the 8259A interrupts the
  CPU directly and the slave registers only store, as INT3 reaches nothing);
  three timers at a quarter of the nominal clock, with timer 2's prescale;
  two DMA channels, unsynchronised or timer-paced, arbitrated by priority and
  halted by DHLT until an IRET; and the chip-select unit's wait states, three
  on the top kilobyte from reset. PC5's POST reprograms UMCS for no waits and
  sets INT0 cascaded, level-triggered and special fully nested at the lowest
  priority, so handlers that end interrupts only at the 8259A keep working.
- **Configurations.** `BoardConfig` holds the CPU, its clock (a
  `time::CpuClock`: from 1 MHz to the 25 MHz of the 80186 family's fastest
  part, its denominator 16 bits, as a crystal's ratio is, so every rate a
  peripheral divides from it is exact; the worker refuses any other clock,
  configured or turbo), the 8255 wiring and conventional memory; `Template`
  gives the IBM PC, the PC/XT, a 10 MHz V20 turbo XT and an 8 MHz 80186
  workstation; video, storage, the ports, expanded memory and the
  coprocessor join it, and the configuration switches derive from what is
  installed.

### 1.3 Video (PC3)

- **Adapters.** Up to two, one monochrome and one colour; overlapping ports
  or memory are refused at configuration, and a window or port a card later
  grows over another's stays with the card that had it. The EGA's and VGA's
  CRT controller and status ports follow the misc output between `3Bxh` and
  `3Dxh`.
- **Beam timing.** Each card renders lazily, one character clock at a time,
  up to the moment it is touched: every register and memory write first
  renders what the beam has passed, so mid-frame changes land where the beam
  was. The 6845 cards' monitor window is measured from the sync pulses, with
  free-running oscillators when a pulse is missing; the EGA's and VGA's
  window is wherever blanking leaves the beam lit, recomputed each frame.
- **Cards.** MDA and Hercules (attributes, ninth column, the Hercules bitmap,
  page and switch, the status bit that tells them apart); CGA (both text
  widths, three 320×200 palettes, 640×200, border, light pen, retrace status,
  CPU accesses waiting for a 16-dot memory slot); EGA and VGA (the planar
  data path with write modes 0–3, colour compare, odd/even and chain-4, the
  attribute controller, the VGA's DAC and its separate serializer and 8-bit
  pairing, split screen, pixel and byte panning, fonts loaded into plane 2,
  the vertical interrupt on IRQ 2). The EGA's and VGA's memory answers
  without wait states.
- **Monitors.** Colour (5153 with its brown, 5154 with 64 colours and its
  200-line IRGB mode, analog VGA), monochrome phosphors (green, amber,
  white), and composite: the CGA's dot clock is four times the colour
  carrier, each colour's chroma a square wave at one of eight phases with the
  burst at colour 6's, decoded over one carrier cycle. The CGA's logic delays
  and a set's chroma filter are not modelled, so artifact hues sit on the
  four demodulation axes.
- **Character sets.** First-party code page 437, authored as text in
  `video/font/`: 8×8 and 8×14 drawn, 8×16 the 8×14 padded with the line,
  block and integral pieces carried to the edges; parsed at compile time.

### 1.4 Storage (PC4)

- **Media** are `storage::BlockDevice`s, synchronous 512-byte sector seams;
  the worker's is answered by the front-end (§3) and a write returns only once
  durable. Floppies are raw images of the seven standard formats or ImageDisk
  archives, which are parsed in the worker as hostile input, bounded, and
  write-protected. A raw image refuses as protected a write it cannot record
  (a deleted mark, a format other than its own layout).
- **The µPD765A** (`storage::fdc`) is selected through the adapter's digital
  output register, as the PC wires it: the DOR picks the drive and gates DMA
  and IRQ 6, and the command's unit number picks only the cylinder register
  and status. Disks turn from their motor's start at the drive's exact speed;
  sectors are found where they pass the head and each data byte moves as it
  passes, over DMA channel 2 or through the data register in non-DMA mode;
  events are processed in the order they fall due. Statuses are per unit,
  sensed lowest first. The high-density adapter adds the CCR and disk-change
  line at `3F7h`.
- **The fixed-disk adapter** (`storage::hdc`): the IBM command block and the
  controller's command set on DMA 3 and IRQ 5, one sector buffer handed to the
  host at the DMA controller's pace, MFM or RLL tracks at 3600 RPM with the
  drive's interleave, and seeks on the drive's own profile when buffered. The
  interleave and bad tracks are the drive's `LowLevel` format, kept by the
  application beside the image (§3).
- **DMA's cost.** Each 8237 transfer holds the CPU off the bus for five
  cycles; the board charges them as it charges refresh, and a transfer
  reaches a card's window as a CPU write does. The HLE INT 13h that serves
  both drives is the BIOS's (§1.5).

### 1.5 BIOS (PC5)

- The 64 KiB system ROM at `F0000h` carries its entry points at the addresses
  PC software calls directly (the reset vector, INT 08h, 09h, 10h, 13h, 16h,
  19h and 1Ah stubs, the INT 1Dh table, the 8×8 font at `FA6Eh`), the model
  byte (`FEh`), and a first-party copyright and date. No IBM text is
  reproduced. Option ROMs: the EGA's or VGA's at `C0000h`, the fixed-disk
  adapter's at `C8000h`, each built for the card it serves.
- Services are host calls in stubs (§0.2); one that waits halts the CPU with
  interrupts on between its steps, one that waits on a port polls it with
  interrupts enabled (`Guest::poll`: reads further apart the longer it waits,
  never past the board's next event, handing back to the stub when an
  interrupt waits), and every service keeps its state in guest memory (the
  data area, bytes its stub reserves on the caller's stack). No poll passes
  the end of the run it is made in: the service tells its stub to ask again
  at once (ZF clear, CF set) and the stub does as the machine runs on, so a
  service holds the machine from its owner for no longer than a slice,
  whatever its state, which the guest may have written over, says
  (`layout::ask_until_done`, the one loop every waiting stub runs).
- Services: INT 08h (tick, motor timeout, INT 1Ch), 09h (scan-code
  translation, shift states, Alt keypad codes, Ctrl+Alt+Del warm start,
  Pause, Ctrl+Break, Shift+PrtSc, the full buffer's beep with IRQ 1 masked
  so keys held through it never nest the handler), 10h (every mode of
  the installed card), 11h, 12h, 13h (floppy with media detection and the
  change line, and fixed disk), 15h (as an XT BIOS answers), 16h (including
  the enhanced-keyboard functions), 18h, 19h (floppy then fixed disk), 1Ah's
  tick count; INT 14h, 17h and 1Ah's clock functions are §1.7's. Both disk
  services set their DMA channel with `chips::dma::channel_setup`, the one
  definition of a channel's port sequence.
- The EGA's and VGA's ROM sets modes from IBM's parameter table, in IBM's
  entry numbering, through the save pointers at `40:A8h`, honouring a
  program's own table, font overrides, palette profile and dynamic save area.
  The VGA's text modes come at 200, 350 or 400 lines (AH 12h BL 30h, for the
  next mode set); cursor emulation moves the CGA's 8-line shapes into the
  cell, the upper half in place and the lower half its distance from the
  foot; AH 1Bh and 1Ch report and save the state; the print screen of every
  row replaces INT 05h on request.

### 1.6 Sound (PC6)

- One mix at the YM3812's rate (the bus oscillator over 288). A source that
  holds a level hands the mixer its changes and their instants, drawn
  band-limited with `lib/audio`'s `Lowpass`; the YM3812 hands it samples. The
  mix is AC-coupled and carried to the stream's rate by `lib/audio`'s
  resampler, whose ratio is steered by at most ±0.5 % to hold the
  front-end's ring at its target (`Resampler::retune` keeps the filter's
  history across a step). The board renders every 10 ms with every source
  caught up; a change past a second ahead of the last render is refused and
  counted, and the stream holds at most a second nothing drained.
- The speaker is timer 2 through port `61h`'s data bit; a tone above the
  mix's Nyquist is heard as its duty.
- The YM3812 is modelled from its documented behaviour: both connections and
  feedback, all four waveforms behind their enable, the rhythm voices and
  their noise, vibrato and tremolo, key-scaled rates and levels, the two
  timers and the status an OPL2 reads with, composite sine mode, and the
  YM3014B's output; its log-sine and exponential tables are computed, and
  its envelope takes the manual's attack and decay times.
- Sound Blaster 2.0: the DSP command set of firmware version 2.02 (8-bit
  single-cycle, auto-initialised and high-speed DMA both ways, 2-, 2.6- and
  4-bit ADPCM with the decoder state carried between blocks, direct output,
  silence, the speaker's ramps, the time constant and block size,
  identification, the test register, MIDI) with the firmware's command
  gating and quirks; `220h` or `240h`, IRQ 2, 3, 5 or 7, DMA 1, the YM3812 at
  its card and AdLib ports.
- A parallel port (§1.7) carries a Covox or the Disney Sound Source (the
  7 kHz FIFO, Select In's latch and power, Ack's full flag).

### 1.7 Ports (PC7) and EMS (PC8)

- The 8250 and 16450 at COM1–COM4, their interrupts gated by OUT2 and held
  off in loopback; adapters sharing a line OR onto it (`Planar::sync_lines`
  drives IRQ 2–7 from every source). The line is levels in time: a device's
  frames at its own rate and framing, the receiver sampling at its own, so
  misframing, breaks, overruns and the framing-error resynchronisation fall
  out of the model. A UART's board event is a character's stop bit or shift
  end, never each sample.
- The Microsoft serial mouse, powered by RTS and DTR, answering `M`; its
  counters saturate at a packet's reach, so a fast flick is lost rather than
  late and a catch-up across any span stays bounded. Every template has it
  on COM1, with a printer at `378h`, a game port and the clock card.
- The printer on a parallel port at `3BCh`, `378h` or `278h` (IRQ 7, 5 at
  `278h`): Strobe, Busy until the Ack pulse its interrupt follows, Init; its
  output kept for the front-end to save (`Board::take_printed`), Busy once
  64 KiB wait.
- The game port at `201h` on IBM's one-shot timing; the front-end feeds it
  (`Board::set_sticks`) from the keyboard or the mouse (PC15, PC16).
- The clock card: an OKI MSM6242B at `2C0h`, modelled from Epson's RTC-62421
  manual (its second source); the front-end sets it from the host's local
  time (`Board::set_clock`) and reads it back to keep the guest's offset
  (`Board::clock`). Its calendar is `lib/abi`'s.
- The POST lists the serial ports (by their IIR), the parallel ports and the
  game port in the data area and the equipment word, and starts the tick
  count at the card's time of day. INT 14h and 17h are the PC BIOS's; INT 1Ah
  02h–05h read and set the card through HOLD and BUSY for 1980–2079, the time
  set with the divider cleared, and 06h and 07h fail as the card has no
  alarm. The ROM records the card's port (`table::CLOCK`).
- The EMS board (`ems`): 1–512 pages of 16 KiB in the memory store, and four
  page registers (two ports each, readable) at one of seven jumpered bases
  showing any page in the frame at `D000h` or `E000h` by page-table update
  (`Memory::show_banked`); the frame is held for the board (`BANKED`) so no
  card or ROM takes it. One more page holds the manager's tables, which no
  register can show. The turbo XT has 2 MiB, the 80186 workstation 8 MiB.
- The INT 67h manager (`bios::ems`) is LIM 4.0 complete, functions 40h–5Dh,
  with an `EMMXXXX0` device header at `F000:0000` where INT 67h points, so
  any DOS detects it; TAIRiX DOS (PC10) also chains a header of that name.
  Handles, names, saved maps and page owners live in the board's spare
  page. Page maps carry a check, so a corrupt one is refused (`A3h`). A
  move or exchange copies at once and then lets its time pass with
  interrupts served; map-and-call leaves the old map's list on the caller's
  stack, and the routine's far return lands on a ROM stub that restores it.
  Alternate map register set 0 is the only set, its state a save area the
  operating system gives; the operating system's functions are locked by a
  key mixed from the moment it is asked for.

### 1.8 The 8087 (PC19)

The coprocessor is modelled from Intel's 8087 data sheet (205835) and the
80287 programmer's reference, whose numerics the 8087 shares; where the two
are silent the 80387 reference's lists of how it differs from them decide.

- **Fitting.** `BoardConfig::coprocessor` puts an 8087 in the socket of
  every board, the 80186's through the 82188 as Intel's data sheet wires it.
  It runs on the CPU's clock, so turbo speeds it too. The configuration
  switch that reports it also lets its interrupt reach NMI, as on IBM's
  planar; an empty socket leaves the CPU's TEST pin high, so a WAIT with no
  8087 waits forever, interrupts served, as an FPU-less PC hangs.
- **The interface.** The CPU computes an ESC's operand address and makes
  its dummy read (PC1), then hands the bus the instruction
  (`Bus::escape`): its eleven opcode bits, the ESC opcode's physical
  address (no prefixes, as the 8087 records it), the operand's physical
  address and the word the dummy read carried. The 8087 reads an operand's
  remaining words at once and writes a result when its instruction ends,
  each time as bus master: the request/grant exchange's four clocks and
  four clocks and the page's wait states a transfer, taken from the CPU.
  WAIT asks when TEST next reads low (`Bus::test_low_at`) and costs
  `3 + 5n` clocks, n the times it found TEST high; it yields at the slice
  limit and is resumed where it was, an interrupt taken with WAIT as the
  return address.
- **Concurrency.** The numeric execution unit runs one instruction at a
  time, alongside the CPU: an instruction's result is computed when it
  starts and committed when it ends — registers, status, the memory it
  stores and the interrupt it raises — that instant a board event. The
  control unit's instructions (FNINIT, FNCLEX, FNSTSW, FNSTCW, FNENI,
  FNDISI) act at once and never hold BUSY; FNINIT abandons the instruction
  in flight. A numeric instruction issued before the last one ends, which
  software must not do and the WAIT every assembler emits prevents, ends
  that one early, so its effects land at once, and starts. FNSTENV and
  FNSAVE hold BUSY as long as they take.
- **Arithmetic.** Exact over the 64-bit significand, rounded once in the
  control word's mode at its precision (add, subtract, multiply, divide
  and square root only); every other result is exact or rounded to 64
  bits. The 8087's own semantics hold where it differs from IEEE 754 as
  finished: projective infinity by default (one unsigned infinity, compared
  equal to itself and not comparable with anything else); one kind of NaN,
  any arithmetic operand of which is invalid, the larger one the masked
  result; unnormals and pseudo-zeros as valid numbers, a single- or
  double-precision denormal loaded as the equivalent unnormal, and the
  80287 reference's unnormal arithmetic (an add normalized as its larger
  operand is, a product with an unnormal factor and a quotient of an
  unnormal dividend left unnormal, an unnormal divisor, modulus, square
  root, integer or BCD store invalid, compares and FRNDINT normalizing
  first); a masked overflow giving infinity in chop mode too, with the
  precision flag; masked underflow flagged on tininess when chopping and
  on tininess with loss otherwise; FXTRACT of zero giving two zeros; the
  constants truncated whatever the rounding mode; condition codes left by
  FINIT and an incomplete FPREM; tags honoured over a register's bits, as
  FLDENV and FRSTOR can make them disagree.
- **Exceptions.** Invalid, zero-divide and denormal are found before an
  operation and, unmasked, abandon it; overflow and underflow, unmasked,
  leave a register destination its result with the exponent moved by
  24 576 and refuse a memory one; precision, unmasked, completes. Masked
  responses are the 80287 reference's table. An unmasked exception sets IR;
  with IEM clear it raises INT and holds BUSY until it is cleared.
- **Transcendentals** are computed in 128-bit significands and rounded once,
  correctly rounded unless the true value lies within 2^-120 of a boundary,
  in the operand ranges Intel documents (FPTAN `0 ≤ x ≤ π/4`, FPATAN
  `0 ≤ y < x`, F2XM1 `0 ≤ x ≤ ½`, FYL2X `x > 0`, FYL2XP1 `|x| < 1 − √2/2`),
  FPTAN answering tan x over one; a logarithm of a power of two and a power
  of two at an integer are exact. Outside those ranges, where the 8087's
  answer is undefined, they answer as the 80387 does. Every series is bounded
  in its terms, so no operand runs one away.
- **Encodings** the 8087 reserves act as the 80387's undocumented aliases
  where it has one (FSTP1, FCOM2, FXCH4 and the rest), else as FNOP.
- **Timing.** Each instruction takes the typical clocks of Intel's table,
  the 80287 reference's where the 8087 sheet gives only a range: FMUL by a
  short operand (40 trailing zero significand bits) its faster row, a
  masked denormal 33 clocks more, an unmasked overflow 14 and underflow 16.
- **Not modelled.** FPREM's wrong quotient bits for 64^N + 1 and 64^N + 2,
  which the 80387 reference names without saying what they were; the exact
  terms of FPTAN's ratio.
- **NMI.** Port `A0h`'s bit 7 enables NMI, cleared at reset and set by the
  POST; its sources are the 8087's INT behind the switch (parity and
  channel checks never fire). The line's rising edge is latched until the
  CPU takes it, so a held INT interrupts once. The 80186 sets DHLT as it
  takes NMI, halting its DMA until the IRET.

## 2. TAIRiX DOS (PC9–PC13)

- **The format (PC9).** `lib/fat` is the one FAT12/16/32 format: the
  parameter block and the volume's regions (FAT32 told by shape, FAT12 and
  FAT16 by cluster count; clusters bounded by the sectors, the table, the kind
  and, through `clusters_within`, the device), table entries of every width,
  short and long entries with their field map, aliases and labels, stamps over
  `DosTime`, `FSInfo`, and a new volume's plan and system area. The FAT32
  driver, `lib/fsprobe`, the `fat32_image` fixture and `lib/fsmeta`'s Atari
  attributes read and write through it. The driver mounts no further than a
  volume's sectors, table and device reach, formats with the boot sector
  last, refuses a file whose first cluster lies outside the volume, and
  refuses to move a directory whose `..` is damaged before writing anything.
  `lib/partition` writes an MBR entry's type byte, active flag and the CHS
  addresses an INT 13h geometry gives its extent (`encode_entries`), and picks
  the FAT12, FAT16 and FAT16B type DOS gives a partition (`fat_type`).
- **Boot.** The disk's volume boot record is real x86 code: it checks for the
  emulator's ROM signature and far-calls the ROM's DOS loader, or prints that
  the disk needs PCEmulator's ROM. The loader reads the BPB, builds DOS's data
  segment, processes `CONFIG.SYS` (`FILES`, `BUFFERS`, `LASTDRIVE`, `DEVICE`,
  `SHELL`, `COUNTRY`, `BREAK`, `STACKS`, `FCBS`) and starts the shell.
- **The kernel** answers INT 20h–2Fh as MS-DOS 5.00 does, and reports itself as
  TAIRiX DOS 5.00 under its own OEM number. Its FAT12/16 layer uses `lib/fat`
  for every on-disk structure. Built-in devices (`NUL`, `CON`, `AUX`, `PRN`,
  `CLOCK$`, `COM1`–`4`, `LPT1`–`3`, and the block devices) have headers in the
  guest's device chain, and DOS calls every device through that chain, so an
  installed driver is called exactly like a built-in one. The default block
  driver reaches the disk through the guest's INT 13h vector.
- **Programs** on disk (`COMMAND.COM` and the utilities) are small stubs whose
  code transfers to the ROM; the behaviour is Rust. `SYS` and `FORMAT /S`
  write the boot record and the system files.
- **Shared folders.** A folder the user granted appears as a drive letter served
  as a network-redirected drive (INT 2Fh function 11h), with 8.3 names mapped
  stably and read-only unless the grant is writable.
- **The default disk** (PC13, `dos::setup`): 30 MB — the Seagate ST-238R's
  geometry (615 cylinders, 4 heads, 26 sectors) on an RLL controller, the
  ST-4038's (733, 5, 17) on an MFM one — at an interleave of 3. One active
  FAT16 partition from the second track to the last cylinder the BIOS offers,
  labelled, its files stamped with DOS 5's release; `COMMAND.COM`,
  `CONFIG.SYS` and `AUTOEXEC.BAT` (which loads the mouse driver) in the root,
  the utilities, `ANSI.SYS` and `MOUSE.COM` in `C:\DOS`. It is built straight
  onto a sparse medium (`storage::sparse`) by the volume builder, which lays a
  volume out on any block device, so it costs only the sectors with data in
  them; the serial is the caller's.

### 2.1 The kernel (PC10)

- **Where it lives.** The kernel's code is host-call stubs in the system ROM's
  DOS region, behind the signature the boot record checks. Its data is RAM at
  segment `0070h`, laid out as MS-DOS 5 documents its structures for the
  software that reads them: the List of Lists, with the `NUL` header in it;
  the swappable data area, its documented head (critical-error and InDOS
  flags, the last error, DTA, PSP, return code, current drive, break flag)
  first; the CDS, DPBs, SFTs, disk buffers, PSPs, MCBs and environments. The
  built-in device headers are in RAM, each strategy and interrupt entry a far
  jump into the ROM, so the chain is ordinary memory a driver is linked into.
- **Calls in progress.** An INT 21h call pushes the caller's registers on
  the caller's stack, as DOS does, and records that SS:SP in the current PSP.
  The call runs as a *root* on a bounded stack of frames in the swappable data
  area, each frame one routine's phase and locals. A routine runs in Rust until
  it needs guest code — a device driver's strategy and interrupt routines,
  INT 13h, 16h, 1Ah, 24h, 28h — then the engine performs the call as the CPU
  would (a far call, or an INT frame), returning to a landing pad in the ROM
  whose host call resumes the top frame. Nothing about a call in progress is
  held in Rust, so a snapshot taken while a program waits at a prompt resumes
  it. A call made while another waits — from an INT 24h or INT 28h handler, or
  a TSR — is a root nested on top, with its own guest stack and scratch
  buffers, one region per nesting level as DOS keeps a stack per kind of call;
  three levels exist, and a call past them or past the frames fails. Each
  level's guest stack ends at a canary the engine checks before resuming a
  frame: a level a handler ran through halts the machine with DOS's
  "Internal stack overflow".
- **Devices.** Every device is called through its header. The built-in block
  driver keeps one unit per floppy drive and per FAT partition of each fixed
  disk and reads the disk through the guest's INT 13h vector, splitting
  transfers at DMA boundaries. A failed call is made again after a reset, up
  to three tries, keeping only AX to repeat it; a write-protected medium or
  an empty drive's timeout stands at once. Media check is answered from the
  change line, and a volume is told by its serial number, label and BPB, so
  a diskette put back under held writes takes them and a stranger is refused
  them; a change met by a read that learns the medium is retried, one a
  transfer meets stands. `CON` reads through INT 16h and writes through INT 29h; `CLOCK$`
  keeps the date as DOS does and takes the time from the tick count, and the
  clock card's at boot; `AUX`, `COMn`, `PRN` and `LPTn` call INT 14h and
  17h, the COM ports set to 2400 baud and 8N1 at boot as DOS's `RSINIT`
  does. A device error is the INT 24h DOS raises, on the caller's stack with
  the caller's registers above it, and the handler's answer is honoured as
  DOS honours it: a call the handler fails keeps its own error, and function
  `59h` then reports 83, failed on INT 24h.
- **Waiting.** Console input asks `CON` for a key, and while none is there
  calls INT 28h and halts until the next interrupt, so a machine at a prompt
  is idle, not polling.
- **Line input.** Function `0Ah` is one line editor whatever the standard
  input is: a console's keys, or a file's or another device's bytes read as
  function `08h` reads them, edited and echoed alike as DOS 4.0's `STRIN`
  does — an LF before the first key dropped, a later one a new line on the
  screen only — the input's end ending the line.
- **Files.** FAT12 and FAT16 through `lib/fat`, cached in the `BUFFERS` disk
  buffers, written back when a buffer is reused, a file is committed or
  closed, a disk is reset, a call that changes a directory ends (MKDIR,
  RMDIR, DELETE, RENAME, a new entry and their FCB forms, as DOS 4.0's
  `FLUSHBUF` calls), and on every drive when a process ends, its errors failed
  without asking. Whole sectors of file data move by direct
  multi-sector requests to the driver. Every chain walk, directory walk and
  path is bounded by the volume it is on. A change of medium keeps each
  drive's current directory by its path and marks its cluster unknown;
  function `47h` checks the medium and looks an unknown one up again,
  leaving the drive at its root when the new medium lacks it, as DOS's
  `ValidateCDS` does.
- **Processes.** EXEC loads COM and MZ programs (relocated, minimum and
  maximum allocation honoured), overlays and load-without-execute; the
  terminate address is the parent's return address from its EXEC call.
  Termination closes the process's handles, frees its memory, restores its
  vectors, writes the terminate address into the parent's saved frame and
  returns through it; INT 27h and function `31h` keep memory. INT 23h
  restarts the interrupted call or ends the program by how its handler
  returns.
- **Drivers loaded from the disk.** `ANSI.SYS` and `MOUSE.COM` are stubs
  whose entries far-call the ROM with DS their own segment, where all their
  state lies. `MOUSE.COM` finds the serial mouse by powering each COM port's
  mouse down and up and listening for its `M`, waiting with interrupts on,
  and serves INT 33h `00h`–`24h`. Its graphics cursor in the planar modes
  reads back and restores the graphics controller where the card can (the
  VGA) and leaves the BIOS's values where it cannot (the EGA).
- **`STACKS=`** hooks the NMI and IRQ 0–6 through ROM entries that switch to
  a free DOS stack, chain to the handler, and switch back when it returns;
  none free, or a stack's bookkeeping damaged, halts the machine with DOS's
  message.
- **`CONFIG.SYS`** is read by the boot task through the same file routines;
  a `DEVICE=` driver is loaded as an overlay and initialised through its
  header, and a character driver named `CON` or `CLOCK$` becomes the system's.
- **Shared folders (PC16.7)** are served by the kernel itself
  (`dos::redirect`), not by a guest redirector: TAIRiX DOS keeps its call
  frames in the swappable data area where DOS 4 keeps the redirector's
  operands, so INT 2Fh's `11h` services are not offered, and no guest network
  software runs. A share's CDS is marked network, with `X:\` its root and no
  DPB, so its paths are made canonical as any are; it takes the first letter
  within `LASTDRIVE` no disk has, given after the boot's drivers have taken
  theirs. Each path call forks before `Resolve`, each handle routine at its
  device branch, and each FCB routine after its drive (`dos::fcb::remote`);
  every request is answered in one step through the board's `Folder`, the
  machine stopped. A remote SFT entry carries the `8000h` bit, the CDS as its
  device and the share's handle where a local one's directory sector lies,
  cleared once the share goes, after which a call through it is "network name
  deleted". A search's place — a listing and an index — lives in the DTA past
  its pattern, or over an FCB's search fields, its drive byte under `80h`. The
  protocol (`folder`) is in host terms (lengths, instants on the machine's
  clock); every path crosses in DOS's spelling, refused unless canonical.
  The front-end's server names host entries in 8.3 form, keeping each name
  and place for as long as a directory's listing is kept, renames in place,
  and holds the folder only on the disk worker.

### 2.2 The shell (PC11)

- **On the program host.** `COMMAND.COM` is a program like the utilities: a
  stub on the disk whose behaviour is `dos::shell`'s routines on
  `dos::program`'s frames, its state — the line, the master environment, the
  batch blocks, a `FOR` in progress, the blocks a command holds — in its own
  memory. It reaches DOS only through INT 21h, and holds nothing of a
  command in Rust.
- **Start.** `/P` is the primary shell: `AUTOEXEC.BAT` from the boot drive's
  root, or `DATE` and `TIME` without one, and no end. `/C` runs one command
  and ends with its code; another shell ends at `EXIT` or at its input's
  end. `/E:n` asks for 160
  to 32,768 bytes, raised to hold an inherited environment whole; past
  32,768 whole variables are kept while they fit and the shell says "Out of
  environment space". `COMSPEC` names a directory the shell is told it is
  in once `COMMAND.COM` opens there, else stays as inherited, else names the
  boot drive's root.
- **Commands.** MS-DOS 5's internal set — `BREAK`, `CALL`, `CD`, `CHCP`,
  `CLS`, `COPY`, `CTTY`, `DATE`, `DEL`, `DIR`, `ECHO`, `EXIT`, `FOR`,
  `GOTO`, `IF`, `LH`, `MD`, `PATH`, `PAUSE`, `PROMPT`, `RD`, `REM`, `REN`,
  `SET`, `SHIFT`, `TIME`, `TRUENAME`, `TYPE`, `VER`, `VERIFY`, `VOL`, by all
  their names — with its messages and switches. `DIR` asks for the drive's
  current directory before listing, as DOS's does, so a directory a change
  took away gives way to the root. External programs are searched as named,
  then with `.COM`, `.EXE` and `.BAT`, in their own directory or the current
  one and `PATH`'s.
- **Lines.** Stages split at `|` outside quotes pass their output through
  temporary files function `5Ah` makes in `TEMP`'s directory or the current
  drive's root, each deleted once read; `<`, `>` and `>>` redirect, the last
  of each counting. The parse is pure functions over bytes in
  `dos::shell::parse`.
- **Batch files** are reopened for each line at the offset the last one
  ended, as DOS reads them; `CALL` links a new block to the caller's; a
  label is compared to eight bytes and `GOTO` searches from the file's start.
- **Handlers.** INT 24h and INT 23h are roots on the shell's own stack. While
  one asks, the standard input and output of the process it interrupted are
  the console — the shell's own standard error, which follows `CTTY` — and
  the answer is read through function `0Ch`'s flush, so type-ahead never
  answers it. A console with no answer left fails the call where DOS allows
  it, else aborts it, and ends a batch file. A failure answered there ends the command with nothing more
  asked or said: the program host reports a call the handler failed as
  error 83, from `59h`. Blocks a command holds are recorded and freed
  however it ends — finished, broken into, or its batch file ended.
- **Drive letters** are made as `COMMAND.COM` makes them, `A` plus DOS's
  number in a byte, whatever a hooked INT 21h answered; the prompt's `$P` on
  a drive DOS cannot read is "Current drive is no longer valid".
- **Not provided:** INT 2Eh.

### 2.3 The utilities (PC12)

- **On the program host.** Each utility is a program like `COMMAND.COM`: a
  stub file (`utility::FILES` names each) whose code transfers to the ROM,
  its behaviour `dos::utility`'s routines, its state in its own memory. It
  reaches DOS only through INT 21h, 25h and 26h and the block driver's
  generic IOCTL, as DOS's own utilities do, so it works on any block device
  that answers them, an installed driver's included.
- **The reference.** Where MS-DOS 4.0's source has the utility, its checks,
  prompts, messages and exit codes are followed; what came later —
  `DELTREE`, `MOVE`, `FIND /I`, `ATTRIB`'s `S` and `H`, `MEM /CLASSIFY` —
  follows the later manuals. Where the source's code contradicts what it
  plainly means, the meaning is followed and the module's rustdoc says where.
  A line a utility cannot take gets the messages of DOS's common parser
  (`Refusal`).
- **Shared.** Absolute sector I/O through INT 25h and 26h (`absolute`), a FAT
  held in memory and read or written an entry at a time (`HeldFat`), a
  report's ten-column figures (`figure_line`) and an input's lines through a
  buffer (`NextLine`) are one definition each.
- **An input's end.** Keys and lines are read through the program host's
  `Key` and `Line`, which tell an input that has ended (`ENDED`) from an
  answer: a Ctrl+Z or a failed read from no console; an empty line from a
  device, or from a file with nothing left. No question asked until it is
  answered can then be asked for ever; each program says what the end
  answers, and `answer_key` makes it no.
- **`FORMAT`.** The switches are checked against each other and the drive by
  one pure function (`format::plan`) before the disk is touched. Each track is
  formatted and verified through the generic IOCTL, then the boot record, the
  FATs and the root are written through INT 26h. The FAT kind is what
  `lib/fat` reads the cluster count as, and the partition's type byte is set
  to match (`lib/partition`'s `fat_type`). `/S` writes TAIRiX DOS's boot
  record and `COMMAND.COM`, read before the disk is asked for; `/B` reserves
  nothing, since `SYS` places the system anywhere.
- **`DISKCOPY`.** COPYINIT's checks of the two drives through IOCTL; read and
  write passes of as many cylinders as the largest free block holds, through
  one drive when both letters name it; the source's format from Get Device
  Parameters or, without a BPB, the old probes; a target of another format
  formatted as it is written; the copy's own serial number; DOS 5's exit
  codes.
- **`FDISK`.** The tables are DOS 4.0's model, pure (`fdisk::table`): each
  disk's master boot record and logical-drive chain, every partition whole
  cylinders, read from sectors, edited, and turned back into the sectors to
  write, nothing written until the program ends. The screens are DOS 4.0's
  message codes drawn by one engine (`fdisk::screen`) through the INT 10h
  calls an XT's BIOS has. A free run's system-area tracks are verified (INT
  13h `04h`), a run a bad one meets left out and the largest found again.
  The logical drives' labels and file systems are asked of DOS: the access
  flag, a volume search, the media ID. INT 23h is ignored and INT 24h fails
  the call. A change that may move letters restarts the machine through the
  POST's warm start.
- **`DOSKEY`.** The resident copy's INT 21h and INT 2Fh vectors lead to
  filters assembled into its own memory, which pass every call but function
  `0Ah` and the `48h` functions straight on in guest code. The commands and
  macros are one buffer (`doskey::store`, pure). The shell reads its line
  through `4810h` once `4800h` answers, so macros expand at the prompt only.
  A Ctrl+C is put back at the head of the keyboard's buffer and the call
  passed to DOS, which breaks as it would.
- **`EDIT`.** MS-DOS 5's editor, from its manual: the menu bar (File, Edit,
  Search, Options, Help), the text window with its scroll bars, the status
  line with the cursor's line and column, the dialogs (Open, Save As, Find,
  Change and its question at each match, Print, Display, the unsaved and
  replace questions, a message, About) and the help window. All of it is pure
  (`edit::ui` over `editor`, `dialogs`, `menus`, `help`, `view`), its state a
  record in the program's memory read and kept at each step. The document is
  a gap buffer over the front of the largest DOS block (`edit::text`); the
  clipboard, and a dialog's directory listing below it, lie at the block's
  end, the document's capacity resized to make room, so neither has a fixed
  ceiling. Each place is found from a known one, so an edit's cost follows
  the distance it moves. The screen is composed as cells and written to the
  active page whole; a key that changes nothing draws nothing. Keys come from
  INT 16h with the shift flags read beside them, so Shift with a keypad move
  selects on the 83-key keyboard. An INT 09h filter in the program's memory,
  guest code, puts the editor's own keys in the BIOS's buffer for Alt going
  down and up and for Ctrl+Ins, which that BIOS has no code for; the mouse
  driver's event handler, guest code too, puts the mouse's key there while
  none is waiting, and the editor asks the driver for the presses, releases
  and position. BREAK is off while it runs, INT 23h is ignored and INT 24h
  fails the call, the device's error said. A save writes a new file in the
  target's directory (function `5Ah`) and replaces the old one only once that
  is closed, passing on its hidden and system attributes. The Display
  settings are kept in `EDIT.INI` beside the program, read as untrusted text.
  The screen found is kept and put back, its mode and font set again where
  `EDIT` set its own. Help is built in; Help Path is not offered.
- **What the program host gives a resident program.** A handler's caller's
  DS is the one its stub pushed. A handler entered again on the same stack
  no deeper than an earlier entry of it was called from drops that root and
  those above it: their caller unwound under them, as a break abandons it.
  The INT 24h handler utilities share (`FailCritical`) keeps the device's
  error it failed a call for in the program's memory, since the call reports
  only that its handler failed it; it and the INT 23h handlers that ignore a
  break or abandon the work for it are one definition each.
- **What the block driver gives them.** Each unit keeps the BPB DOS builds
  for its drive (the *recommended* one), and a formatter's set BPB stands in
  for the medium's until the drive's is set again, as DOS 4's driver keeps
  them. A track formatted through the IOCTL, or by any program through INT
  13h (DOS hooks it), makes the unit's next media check say the disk changed.
  The INT 1Eh table is DOS's copy in RAM, its last-sector field set to the
  medium's for each transfer, so a high-density diskette's multi-sector read
  never runs onto the other head. A format is first asked of the BIOS (INT
  13h `18h`); a fixed disk's tracks are verified as many a call as one
  transfer holds. A partition with no file system is a drive with the BPB DOS
  4 would format it with, its access flag clear until a BPB is set for it.

## 3. The application (PC14–PC16)

- **The machine worker** (`worker`) is this binary re-entered in the machine
  role through `SPAWN_SELF`, over a `lib/sandbox` duplex session whose worker
  end is `lib/sandbox`'s `WorkerLink`, read with a wait, and one spawn share
  holding the frame slots. It is single-threaded: slices of at most 4 ms of
  emulated time, one whenever the machine is 4 ms behind the host's clock,
  never more than 100 ms behind, and a wait on the pipe between them.
- **The protocol** (`link`) is one total codec both ways. The front-end's side
  (`front::Host`) never blocks and checks every event against what it asked:
  a frame within its slot, a request on a medium it named and the one the
  protocol allows, a format within its drive. The first that fails ends the
  worker.
- **Frames** cross by naming a slot — two an adapter, each the size of its
  monitor's largest frame, a larger one reported out of range — which the
  front-end copies out and hands back; an unchanged frame is not sent.
  **Sound** and **sectors** cross in session frames: the share is the
  worker's to write and the front-end's only to copy out of, and their bytes
  are too few to be worth more. A fetch asks for a run of up to 64 sectors, a
  store writes one, and the machine stops while one waits, so emulated time
  never sees the host's storage; a store is answered once the front-end has
  written it, so a failed write is the guest's write fault. The worker keeps
  what it fetched in a `lib/reclaim` clean-file-data cache under the
  front-end's seed, and the last run fetched whatever pressure takes.
- **Input** is credited: the front-end holds what lies beyond a window of 64
  commands. The worker credits a key as it arrives and feeds it at the
  keyboard buffer's pace, so a guest that reads no keys never shuts the
  window on the commands behind them.
- **Media metadata** the images cannot hold — a fixed disk's interleave and
  bad tracks — is kept in the machine's settings and handed back on attach.
- **The clock card** runs at the host's clock plus the machine's own offset,
  which the guest moves by setting its time, as a real card's battery kept
  what it was set to; the offset is kept with the machine. No zone store is
  needed: the application reads no file.
- **The store** is the application's own (`plans/APPDATA.md`). The library
  record — every machine's name, configuration, fixed disks and their low-level
  formats — is one checksummed blob written alternately as `library-a` and
  `library-b`, the newer whole one read, so no write can leave the library
  torn. Each machine adds a blob per fixed disk it owns and one for its state:
  its last screen, compressed, and, while it is suspended, its snapshot. The
  store holds at most 64 blobs, which bounds the library at twenty machines,
  each with both its disks and its state; a disk beyond that is the user's
  own document. The application runs as one instance, so the store has one
  writer.
- **The library record** holds, per machine, a number minted once and never
  reused, its name, its configuration in the session's own codec, each fixed
  disk's drive and low-level format, and its clock offset; a CRC-32 closes it
  and a generation orders the two copies, a copy counting only in the blob its
  generation belongs to. Decoding it is total: a copy that does not check out
  is the other copy, and two that do not are an empty library said as such,
  never a guess — that load sweeps nothing and mints no number a blob carries.
  One record write is under way at a time, the next going to the other blob
  only once the last is on the store; changes made meanwhile are written once,
  together.
- **Creation and deletion are ordered for a cut short write.** A machine's
  disks are made or copied before a record holds it; a deleted machine's
  blobs go only once a record without it is on the store. Every load sweeps
  the blobs no machine in the record owns.
- **The library window** shows each machine as a card with its last screen, its
  specification and its state; creating, duplicating, starting, configuring and
  deleting are its commands, and deleting asks first. A secondary press on a
  card chooses it and opens its menu: *Start* (*Resume* while it is suspended,
  *Show Window* while it runs), *Settings…*, *Duplicate* and *Delete…*, the
  last two only for a machine at rest, and, while it runs, the machine's own
  rows from its *Machine* menu. The cards scroll, and a
  change repaints only the cards it touched. Several machines run at once,
  each in a window of its own over a worker of its own; closing the library
  leaves them running, closing every window leaves the program on the icon
  bar — its slot's click or the *Machine Library* row brings the library back
  — and only *Quit* ends it, suspending every running machine first. A
  suspending machine's window stays open until its state is kept
  (`app::keeping::Suspends`), so a session logging out waits for the write. The first run makes the Turbo XT
  with the default disk. **The new-machine assistant** is an owner-modal
  dialog offering the four templates, the name and the disk choice — the
  default disk made for it, or none; a template with no fixed-disk controller
  is offered none. **Settings** is an owner-modal dialog per machine, its
  controls the shared ones (`lib/controls`) in one field column: a choice list
  stays open under the pointer until a choice or a press elsewhere takes it
  away, a press that takes it away presses nothing beneath it, and a switch
  shows the value it is set to. A running machine's settings open read-only,
  since a change of hardware needs the machine off. Every read and
  write of the store is on the library worker and every running machine's
  sectors on the disk worker, so a long copy never stalls a guest; the loop
  asks and collects. Both workers answer in order, which keeps a machine from
  opening a disk a copy has not finished. **The machine window** carries the screen, the drive lights with
  their media menus, speed, pause, reset, Ctrl+Alt+Del, screenshot and
  fullscreen. It opens to show a VGA screen at one pixel a dot
  (`VGA_SCREEN`, 640×480) above the bar, no larger than the screen holds. Images dropped on the window are inserted read-only; a writable
  disk comes from the picker. A lamp is lit while its drive works — a
  diskette's motor, a fixed disk's command — and held 60 ms of emulated time
  after; the worker sends lamps on change and a lamp of a drive the machine
  lacks ends it. The front-end decides how an image goes in from its size and
  the ImageDisk magic alone, and `lib/browse` types `.img` as a raw disk
  image, `.ima`, `.vfd` and `.flp` as raw floppy images and `.imd` as an
  ImageDisk archive, which is served as no volume. The bar's trailing *Machine*
  button shows a display and *Machine* — *Paused* with a pause sign while it
  is paused, *Saving…* as it suspends — and a down chevron, so it reads as the
  menu it opens; a primary or secondary click on it opens the menu, and a
  secondary click on any slot of the bar opens that slot's. The menu carries
  pause, reset, Ctrl+Alt+Delete, the processor's speed (the settings' speeds,
  for the run), the tube's effects (kept per machine in the record), a
  screenshot (the moment's screen, 4:3 in whole dots, a PNG through the Save
  panel), full screen, which keeps the bar as the way out, and the debugger
  (§3.1). The rows that act on the machine in place may be chosen with the
  menu kept up (`plans/NEW-MENUS.md` M11). Every menu up — bar, drive, share
  or library card — is a `Followed` holding the rows it was last given; once
  per pass of the loop, after the events are in, its rows are built again and
  restated only where they differ, so no state change has to remember it.
- **Snapshots** suspend a machine on close and on quitting, and resume it on
  start; *Shut Down* in the machine's menu turns it off. The snapshot is the
  worker's (`snapshot`): a version, the configuration and fixed-disk drives it
  is of, then every part, each field kept or named as left as built so a
  field added unsaid does not compile, every value checked as read; what
  pages and ports map to is worked out again from the devices, every device
  is brought to the processor's time before one is taken, and a restore
  requires every position within a second of it. It crosses compressed:
  `Suspend` asks, `Kept` pieces and `Suspended` answer, and a resuming worker
  pulls it with `Recall`/`Recalled` before `Resumed` and `Ready`. It is kept
  in the machine's state blob behind its screen, each part checked on its
  own, only once what the machine wrote to its images is durable; on resume it
  is set aside before the machine runs. Diskettes come back out with their
  change lines set, the clock card is set from the host, the BIOS moves its
  tick count on by the time away with each midnight counted (TAIRiX DOS adds
  the count to its date), and the menu's speed was for the run before. A
  snapshot that does not take starts the machine afresh; a suspend not
  answered in ten seconds turns it off. Settings are read-only for a machine
  not off, and the library shows each as off, running, being kept or
  suspended.
- **Copy and paste** are in code page 437, through `lib/cp437`. The worker
  reads adapter 0's text as its controller scans it — the start address, a
  split, a preset row, double scanning, a second Hercules page — on
  `ReadText`, answering `Text` (at most 256 by 128 cells), and says with
  `TextShown` when the adapter goes between text and graphics, which offers
  or withholds *Copy Screen Text*. The window copies each cell's glyph, a line
  a row, trailing blanks and blank rows below left off. *Paste* asks the
  clipboard; the window reads at most 65536 characters and types at most as
  many codes: line breaks press Enter and tabs Tab, and each other character
  is its own code, else its plain spelling (typographic quotes, dashes,
  spaces, the ellipsis), else its letter without the accents the page lacks;
  a combining accent composes with the letter before it, and what draws
  nothing passes unseen. The faces, arrows and suits of `01h`–`1Fh` are control
  codes to a PC — the heart is Ctrl+C — so they are left out, and an alert
  says what was. `Type` carries only bytes that act as no control but Tab and
  Enter, within a typing window of 1024 that `Typed` reopens. The worker
  types each code with its key on the US layout, Shift as the layout and Caps
  Lock call for it, or Alt and its decimal value on the keypad, and begins a
  character only once no key is held, the keyboard has sent everything and
  the BIOS's buffer is empty. A key pressed stops the typing (`StopTyping`),
  and a reset or a suspend drops what is left.
- **Shared folders.** *Share a Folder…* asks the trusted picker for a
  subtree (`plans/APPWIN.md`), redeemed on the disk worker and served there
  as one of four shares, labelled from the folder's name, its times moved by
  the machine's clock offset. `Share`/`Unshare` commands and `Shared` events
  carry a share's life, `Folder`/`Foldered` its requests, one outstanding at
  a time; the host answers a request of a share it stopped itself. The worker
  fetches small reads a 32 KiB piece at a time, forgetting the piece on a
  write or an open of its file, and asking whenever a read reaches past it.
  Each share is a slot on the bar with *Stop Sharing*. A reset keeps the
  shares; a snapshot keeps none.

### 3.1 The debugger (PC20)

- **The probe** (`debug::probe`) is the debugger on the bus, as an
  in-circuit emulator sits on one, held by the board while the debugger is
  attached and never in a snapshot. It holds at most 32 breakpoints, each
  valid and none twice: code (a physical address), memory (a range written,
  or read or written), ports (a range, in, out or both) and interrupts (a
  vector, and AH where given). Every memory cycle on a watched page — the
  processor's, the 8087's, DMA's, and the firmware's host calls acting for
  the processor — and every port cycle, the 80186's control block's
  included, reaches it with its master; code fetches do not. Watched pages
  carry a page attribute the board's special path keys on, kept across
  remaps, and are withheld from translated code's page map, so translated
  code leaves for the interpreter at a watched access and keeps running
  elsewhere. Interrupts reach it from the processor's one entry path and
  from the firmware's simulated INT, with their cause.
- **Boundaries.** The processor asks the bus at each instruction it begins,
  the interrupts due at that boundary taken (`Bus::begins`); a stop there
  marks the boundary's interrupts taken, so the run that resumes is the one
  that would have run. A repeated string instruction paused at a cycle limit
  is not a new instruction and stops nothing but a break; an interrupt taken
  at such a pause returns where one taken inside the instruction would.
  While a code breakpoint, a step or a stop due is held, translated blocks
  are not entered (`Bus::watches_instructions`): they have no boundaries to
  ask at. A watch or an interrupt breakpoint stops at the next boundary; a
  halted or waiting processor stops at once for a break or a stop due.
- **Stepping.** *Step* runs one instruction into what it calls, but a
  handler a pin enters on the way runs to its return. *Step Over* runs a
  CALL, INT, INTO, BRKEM, CALLN, RST or repeated string instruction to the
  next instruction with the stack at or above where it stood. *Step Out*
  watches for the procedure's own return — RET, RETF, IRET, RETEM, and the
  8080's RET and taken Rcc — at or above the frame, and stops where it
  returns to. Stacks are SS:SP natively and DS:BP in 8080 mode.
- **The worker** attaches the probe on `Attach`, holds it across a reset
  without its stop, and takes it off on `Detach`, saying it took each reset
  made with the probe on (`Reset`) and each detach (`Detached`). A stop holds emulated time
  still (`advancing`); a break asked of a held machine runs it only to the
  next boundary. `Stopped` carries the reason — the breakpoint itself, or
  the watch and what it saw — and the registers, the 8087's values each
  written exactly to nineteen digits (`debug::number`). A `Look` is answered
  from the machine as it stands: up to 16 lines before the code address and
  48 from it, decoded by the CPU's one decoder, the 8087's own and, in 8080
  mode, the 8080's, the lines before found by voting across every start
  within a reach of up to 128 bytes, four a line asked; up to 2048 bytes of
  memory and 64 stack words. Every request out of turn ends the session.
- **The host** holds the debugger's requests in order with the credited
  input, each a few bytes, mirrors the probe's set to refuse what the probe
  would, and believes a report only as asked: a stop of a processor running
  under the probe, registers of the machine it is, an answer only to the
  look sent, no more lines than asked and those after beginning where asked,
  memory and stack as long as asked, every line printable and following the
  one before. A reset sent lets go of the stop and any look at it; what the
  worker said before it took a reset or a detach the host sent is dropped
  until it says it took it, so a stop already on its way is never mistaken
  for one of the machine after, and Go waits for a new stop.
- **The window** (`app::debugger`) is a top-level window of the machine,
  opened from the machine's menu: Continue, Break, Step, Step Over, Step Out
  and *Add Breakpoint…*; the status; the listing with its current line and
  breakpoint marks, a press in its gutter toggling one; memory, the
  registers and the 8087 with what changed since the stop before marked, the
  stack and the breakpoints. F5 continues or breaks, F9 toggles the current
  line's breakpoint, F10 steps over, F11 steps and Shift+F11 steps out.
  Addresses are typed as `segment:offset`, an offset alone, a physical
  address or register names. Each look waits for the one out to be answered,
  the latest winning, and each change repaints only the panes it reaches.
  *Add Breakpoint…* is an owner-modal dialog of the shared controls.

## 4. Acceleration (PC17, PC18)

- **BR26.** `code_install` (no. 172, gated by `CAP_JIT_MAP_EXEC`, held by the
  front-end; `docs/src/architecture/syscalls.md`) moves a page-aligned region a
  compiler sandbox wrote out of the compiler's address space and maps it
  read-execute, never writable, into the target's code window, a RAM-sized
  window of its own. Both processes are the caller's distinct, sandboxed, live
  children; a compiler's first install pairs it with that target's address
  space for the compiler's life (`ProcessSpace::pair_code_target`). Everything
  the target can refuse — its address-space bound, room in its window — is
  settled before a page leaves the compiler; the pages the compressed tier
  parked are restored in the same hold of the compiler's space that moves
  them. Every page is cleaned to the point of unification and every CPU's
  instruction fetch fenced past it before any is mapped
  (`PhysMap::fence_instruction_fetch`: riscv64's local and SBI remote
  `fence.i`, which the loader now issues too; a VIPT instruction cache on
  aarch64 is invalidated whole, as Linux does). The target releases its code
  with `mem_unmap`. Proven on every native port by
  `tests/integration/code_install_qemu_{aarch64,riscv64,x86_64}`.
- **The translator** compiles hot blocks in the compiler sandbox, never on the
  worker's critical path: the interpreter runs a block until its translation is
  installed. The code is compiled for a `tairix_codegen::Target` (PC18.6): the
  discovered architecture — `BootFacts`' arch, the kernel-attested port
  identity — and those of the extensions every core has (the startup vector's
  `CpuFeatureSet`, `tairix_rt::cpu_features`) that its backend lowers to,
  never chosen by `cfg`. x86_64 with BMI2 shifts by a register count with
  `shlx`/`shrx`/`sarx`, the count left where it lies, and rotates by a
  constant with `rorx`; riscv64 with Zbb rotates with `rol`/`ror`/`rori` and
  extends with `zext.h`/`sext.b`/`sext.h`. `Target::ALL` names every target a
  backend lowers differently; the compile request carries one by its place
  there, and every conformance check and the translator's differential run
  over each.
- **`lib/codegen`** (PC18.1) is the one code generator `plans/BROWSER.md`
  decision 6 names, serving BR27, BR28 and `plans/UNIVERSAL.md` U2 as well as
  this translator. Its IR is SSA over `I32` and `I64` values in blocks with
  parameters: integer arithmetic, logic, shifts and rotates, comparisons and
  selects, 8- and 16-bit extension, loads and stores at a base plus an offset,
  calls through a table of helpers the code is entered with, jumps, branches
  and returns. Every operation is total — a division by zero gives zero and
  its remainder the dividend, a signed overflow wraps, a shift counts modulo
  the width — so no input traps the host. A verifier refuses an ill-typed or
  ill-formed function, and an interpreter is the reference every backend is
  held to. Registers are allocated by linear scan over the blocks in order:
  a value live across a call prefers a callee-saved register, and in a
  caller-saved one the call saves it around itself; with none free the
  interval read least for its length takes a stack slot; a few registers
  per target stay out of allocation as scratch. Each
  backend lowers to a list of its own machine instructions, the encoder's
  only input, so a backend is tested twice over: that list run on a model of
  its machine against the IR interpreter, and each instruction encoded and
  decoded again by `lib/disasm`. Dead pure instructions are dropped,
  constants folded where a target encodes them, and a branch — and on
  x86_64 and aarch64 a select — on its own block's comparison tests it
  directly; a branch falls into whichever successor is laid out next.
  Output is position-independent and
  makes a frame record, so the system's frame-pointer backtrace passes
  through it; branches are relaxed to their reach, and a function past a
  target's longest reach is refused, not miscompiled.
- **The front end** (PC18.2) lowers a block to one IR function entered with
  the frame, the page map and the helper table. A block begins at a step
  boundary with no prefix pending, no stale queue byte, TF clear and the
  processor in its native mode, and holds at most 32 instructions. It ends
  at a control transfer, at STI, at a segment load that shadows the next
  instruction, and before an instruction it does not translate: port I/O,
  interrupt entry and return, `HLT`, `ESC` and `WAIT`, a host call, `LOCK`,
  a repeated string instruction, `POPF`, `BOUND`, `ENTER`, the NEC
  extensions, and what loads CS other than a jump; a block that fills runs
  on, one stopped short leaves the next instruction to the interpreter.
  Each instruction first checks what it will touch — every load and store
  plain RAM in the page map, no store into a page holding translations, no
  word across a page or a segment's end, no divide error — and the block
  exits before it, unchanged, where one fails, so the interpreter takes that
  instruction with its own queue model. An instruction stores to the frame
  only what it changed, once, as it ends, so every exit of a kind shares one
  return. It counts its cycles exactly as the step loop does — the bus
  unit's fill, credit and bus cycles, the pages' wait states, DRAM refresh
  charged through the bus where its deadline falls — and the block exits
  once the cycle limit is reached, so devices and interrupts see the same
  instant as under the interpreter. Status flags are kept as the operation
  that set them: a condition reads its operands, so a compare and branch is
  one host compare, and the word is computed, by the interpreter's own
  `alu` functions, only where something reads all of it; a block may leave
  the operation in the frame for `Cpu::adopt` to finish. Arithmetic the
  interpreter computes in microcode loops (shifts, multiply and divide
  timing, the decimal adjusts) is the interpreter's own function, called as
  a helper. Proven (PC18.5) by `cpu::jit::differential` (behind
  `test-util`): a random machine and random code, the block run through the
  IR interpreter and each target's model (`tairix-codegen`'s `test-util`),
  each held to the CPU interpreter stepping to the same cycle — processor,
  memory, pending waits, refresh and every helper call with its arguments,
  each helper's arity `helper::ARITY` — the models refusing an undefined
  register, a clobbered callee-saved register or stack, a misaligned call
  and a missing frame record. The unit test covers every exit and
  instruction kind on a fixed seed; `fuzz_translator` is the fuzz target.
- **The code cache** (PC18.3) lives in the machine, keyed by CS:IP in 4096
  direct-mapped slots, with direct-mapped heat counters: a place the
  interpreter reaches 32 times is requested, its bytes read only from RAM or
  ROM a block may be translated from. The board's store is watched in
  256-byte granules from the request on; a write to one by anything — CPU,
  DMA, the expanded memory manager, a restore — or a bank switch or control
  block move away from it makes it stale, whatever address reached it, and
  drops every block and request over it before the next block is entered. A
  granule gone stale four times is left to the interpreter while its churn
  lasts. The page map holds, per 256-byte page, a pointer into the store or
  none — device memory, an unmapped window, wait states varying within a
  kibibyte — its wait states, and whether a store may be made: never into a
  watched page. It is kept as the memory changes, 4 KiB at a time. A block
  is entered only where the bus is owed no wait. The entry ABI is the
  frame, the page map and the helper table: `extern "C"` arguments as
  64-bit words, an `Exit` answered; the refresh helper is the bus's, every
  other the interpreter's own. Blocks run through an `Execute`; the IR
  interpreter's (`cpu::jit::interpreted`) runs whole machines held to the
  CPU interpreter.
- **The compiler sandbox** (PC18.4) is `Run` re-entered as a one-shot
  worker serving `compiler`, holding nothing (`cpu::jit::compiler`). The
  worker numbers each block as it asks for it — its bytes and where they
  begin — and keeps at most `COMPILE_WINDOW` (four) unanswered; an answer
  installs only the request it names. The front-end's compile worker thread,
  never its window loop, holds one compiler per machine, tells it the
  target, and the compiler translates and compiles
  the bytes alone, refuses code past `MOST_CODE_BYTES` (256 KiB, the heaviest
  block measured some 230 KB), and stages it in fresh pages of its own
  (`tairix_rt::stage_code`). The front-end — holding `CAP_JIT_MAP_EXEC` by the
  bundle's `AppInfo` — moves them into the worker with `code_install` and
  answers where they landed; it never reads the code. Both roles, and the
  front-end's hold on a machine's compiler, are `roles`, which `Run` and the
  cross-target verticals' fixture play alike. A compiler that
  crashes, overruns its ten-second deadline or answers what cannot be
  believed is contained and replaced, the block left to the interpreter; its
  third failure, a compiler that cannot be started or a platform that refuses
  the install's fence tells the machine to interpret, and a session without
  the capability or a backend interprets from the start. A block that answers
  no exit leaves the machine interpreted from then on: the worker says so
  once (`Interpreting`), the front-end answers any block it asks for itself,
  and the application reports it and lets the machine's compiler go. The
  worker runs the
  code through `cpu::jit::native`, the engine's only `unsafe`, enrolled in
  miri through stand-in blocks: the frame is entered beside the environment
  the refresh helper reaches through the one pointer the code hands back, the
  page map is aligned words, and the pure helpers share one five-argument
  trampoline over the interpreter's `helper::call`. Installed code is a
  `TransformCache` within a sixteenth of the worker's room, given up whole
  once past it and at moderate pressure, unmapped as each block goes. A
  machine turned off has its worker killed but not reaped until the compile
  worker has forgotten it, so its pid cannot name another child while an
  install may be in flight.

## 5. Verification

- Every decoder of untrusted input has a fuzz target in the change that adds it:
  the instruction decoder, the ImageDisk reader, the BPB and directory decoders
  in `lib/fat`, the DOS EXEC loader (MZ headers, relocations), the session
  protocol in both directions, and the translator differentially against the
  interpreter, and the 8087 over hostile instruction streams (`fuzz_fpu`).
  So does every service a guest calls with hostile registers:
  the BIOS over a written-over data area on every adapter (`fuzz_bios`), the
  EMS manager, TAIRiX DOS's INT 21h, 25h and 26h (`fuzz_dos`), INT 33h
  under motion and mode changes (`fuzz_mouse`), and `COMMAND.COM` typed at
  with hostile lines and running hostile batch files, every line ending in a
  wait for a key and leaving the shell only its own two blocks
  (`fuzz_shell`).
- CPU conformance vectors per instruction and model, including flags and cycle
  counts; a boot test that runs the default disk to the `C:\>` prompt and reads
  it from the text screen; a test that boots a hand-made MS-DOS-style boot
  sector from a floppy image.
- QEMU verticals on every native target (PC21,
  `tests/integration/pcemu_qemu_{aarch64,riscv64,x86_64}`) boot the production
  kernel and image and run the `pcemucheck` fixture from the scripted shell.
  Its reference run (`digest::reference_run`: the turbo XT on its default
  disk, interpreted, to past DOS's prompt, its whole state folded every half
  second) must give `REFERENCE_DIGEST`, the constant the host suite asserts
  too, so every target's compiler computes the same machine. Then it boots
  the default machine in its sandboxed worker, its compiler sandbox's blocks
  installed with `code_install`, puts a diskette in A: once DOS is up and
  runs `LOOP.COM` from it — five million additions, long enough for its
  loop to be compiled — until the program has printed their sum; DOS and
  the BIOS run as host calls, so only a program's own code gets hot. Like
  the app, the fixture watches the memory-pressure notice and tells its
  worker the band: a host that reports none leaves the worker at the
  fail-closed critical band, with no room for translated code at all. The
  fixture's worker counts the blocks its native executor ran into its
  share's tail (the share made that much longer than the layout, in whole
  pages as the kernel records a region), and the fixture passes only with
  the right sum and some native runs.
- `unsafe` lives only in the entry into installed code, enrolled in miri,
  and in the one promise each binary that builds a native executor makes as
  it does — `Run`, and the cross-target verticals' fixture. The
  share is reached through `lib/rt`'s mapping, and a slot changes hands only
  across the pipe, whose write and read order it, so no ordering in the share
  needs a model.
